# Translations

Three languages ship complete: **Lao, Thai, English**. The other fifteen from the old project are carried
along as a starting point and filled in over time. A language is either complete or clearly marked
incomplete; a screen half in English is worse than a screen entirely in English.

## Reusing the old project's files

Source: `Buncheengern/.claude/worktrees/v2-phase3.4c-responsive-nav/i18n/`, eighteen `lang_*.js` files
plus `lang_meta.js` and `currencies.js`.

They are a **translation memory, not a dependency.** Nothing is imported at build time and nothing links
back to that repository. A string is copied across only when the new key means the same thing as the old
one — same meaning, same tone, same length constraints.

What transfers cleanly:

- Money words: amount, currency, cash, total, price, paid.
- Everyday verbs and states: save, cancel, delete, search, today, yesterday, loading, error.
- Currency names and symbols from `currencies.js`, which becomes seed data as-is.
- Flags and language labels from `lang_meta.js`, essentially unchanged.

What must not transfer:

- Anything naming a concept this project does not have: branches, Google sign-in, the Split payment mode,
  the currency-adding flow, the offline queue.
- Anything implying an entry can be edited or deleted. Reusing "edit" or "delete" phrasing would put
  words on screen for capabilities that do not exist.
- Anything about closing the day by hand. The day closes itself; a string saying "close the day" would be
  describing a button that is not there.

Everything genuinely new needs writing from scratch: reversal versus refund, the drawer count, the
authenticator and recovery codes, the screen lock and PIN, linked sign-in methods, sessions and devices,
the chain and its verification, the unreachable-server page, and the admin sections.

## Key structure

Keys are grouped by screen or by concern, not by language, and each language is a separate file loaded on
demand rather than all eighteen shipped to every device.

```
src/i18n/
  en/  common.json  auth.json  record.json  today.json  notes.json
       reports.json  settings.json  admin.json  errors.json
  lo/  …
  th/  …
```

Rules that prevent the usual mess:

- **Keys are meaning, not text.** `record.confirmSaveTitle`, never `record.areYouSure`. Rewording English
  must not require touching every other language's file.
- **English is the reference.** A missing key falls back to English and is reported by a check that lists
  every gap per language, so nobody discovers it on a phone.
- **No sentence assembly from fragments.** Word order differs across these languages, and concatenation
  produces nonsense in at least one of them. Whole sentences carry their own placeholders.
- **Plurals and number formatting go through the platform's own formatting**, not hand-written rules. Lao
  and Thai have no plural inflection; English does.
- **No text in images or icons.**

## Two independent language settings

The interface language belongs to the person using the app. **The receipt language is a separate setting**
that belongs to the shop, because the person reading a printed receipt is usually not the person who
recorded the sale. Changing one must never change the other.

## Lao and Thai specifics

The previous project shipped a real bug here, and it is worth not repeating: line-height and font fallback
were scoped incorrectly, so Lao and Thai text clipped. Both scripts need more vertical room than Latin,
and the rule must attach where the language is actually declared rather than to a bare selector.

Verify by rendering, not by reading the stylesheet: a long Lao string in a button, a Thai string in a
table cell, and a mixed Lao-and-numerals total, each checked in the browser.
